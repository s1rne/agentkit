# Параллельная работа

## Когда можно

Одновременно — только если выполнены **все** условия:

1. **Множества `touches` не пересекаются.** Главный критерий: два агента, правящих один файл, гарантированно затрут друг друга.
2. **Нет зависимости по результату.**
3. **Нет общей миграции.**
4. **Ни одна задача не `risk: high`.**

Не выполнено хоть одно — последовательно.

## Сколько

Считается по алгоритму навыка `team-composition`, потолки ролей — в `TEAM.md`. Общий потолок одновременных — **5**: больше не ускоряет, потому что результаты приходится сшивать вручную и лид перестаёт понимать, что происходит. Машина накладывает второй, независимый потолок — по RAM, диску и нагрузке; его показывает `agentkit context`. **Всегда действует меньший из двух**, см. `resource-limits`.

## Как запускать

Все параллельные вызовы — **в одном сообщении**, иначе пойдут последовательно.

Каждому агенту передаётся: путь к файлу задачи; его `touches` с явным запретом выходить за них; какие навыки загрузить; требование сдать отчёт по `handoff-protocol`.

Формулировка границы: «правь только файлы внутри `touches`. Понадобилось чужое — останови работу и напиши в раздел „Вопросы“, не правь».

## Сбор результатов

1. Дождаться всех.
2. Свести отчёты: сделано, не сделано, найдено попутно.
3. Проверить, не полез ли кто за границы.
4. Запустить `critic` на каждую задачу — тоже параллельно.
5. Свести находки.
6. Записать в `RUNS.md`, позвать `scribe`.

## Разбор споров

Два агента предложили несовместимые решения — **не выбирай сам**. Позови `architect` и дай оба варианта. Архитектурный спор решает архитектор, а не тот, кто сдал первым.

## Когда параллельность вредит

- Задачи плохо описаны — параллельность умножает недопонимание на количество агентов.
- Предметная область неясна — получишь несколько разных неверных толкований вместо одного.
- Первый модуль проекта — сначала эталон последовательно, потом по нему параллельно.
