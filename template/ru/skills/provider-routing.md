# Маршрутизация работы по провайдерам

## Роль просит возможность, а не провайдера

Роль никогда не называет `claude` или `cursor-agent`. Она объявляет, что нужно работе, а маршрутизатор выбирает среди провайдеров, в которые **сейчас реально выполнен вход**.

| Возможность | Что означает |
|---|---|
| `code` | править файлы репозитория и запускать его инструменты |
| `bulk` | много дешёвых однотипных проходов — переименования, массовые правки |
| `images` | читать скриншоты, макеты, схемы |
| `big-context` | в одном контексте должен уместиться большой объём материала |
| `plan-mode` | выдать план, не трогая рабочее дерево |
| `worktree` | работать в изолированной копии на своей ветке |
| `parallel` | несколько экземпляров роли одновременно |

Название провайдера вместо возможности делает задачу невыполнимой в тот момент, когда на машине нет входа именно в него.

## Только подписочные CLI

Разрешены **`claude`** (Claude Code) и **`cursor-agent`**. Оба авторизуются собственным входом по подписке.

**Никакого поштучного HTTP API. Никаких ключей.** Поштучное потребление тарифицируется отдельно и дорого: флот, тихо свалившийся на API-ключ, превращает фиксированную подписку в счёт за токены, которого никто не утверждал, и счёт приходит уже после работы.

Отсюда:

- переменные с ключами и подменой адресов **вычищаются** из окружения дочернего агента — именно удаляются, а не обнуляются, чтобы CLI вернулся к сохранённому входу;
- провайдер, чья авторизация разрешается в поштучный режим, **не выбирается никогда**, даже если он единственный с нужной возможностью. Вместо этого задача блокируется;
- если такая переменная выставлена в оболочке самого человека, лид сообщает об этом одной строкой. Молча обходить это нельзя.

## Изоляция аккаунтов

Разные аккаунты разделяются **каталогом конфигурации**, а не ключом: `CLAUDE_CONFIG_DIR` для Claude Code, `CURSOR_CONFIG_DIR` для cursor-agent. По каталогу на аккаунт, постоянному между прогонами, чтобы вход не терялся.

## Одного Claude Code достаточно

Вся система работает на `claude` и больше ни на чём. Остальные провайдеры **добавляют** возможности, но не являются условием запуска. Правило, делающее второго провайдера обязательным, — ошибка в правиле.

## Отсутствующая возможность блокирует одну задачу, а не волну

Если ни у одного провайдера с выполненным входом нет нужной возможности:

1. **Эта одна задача** переходит в `blocked` с указанием недостающей возможности.
2. **Точная команда, которая это чинит**, записывается в задачу и сообщается человеку одной строкой — например `cursor-agent login`.
3. **Всё остальное продолжает работать.** Волна не останавливается из-за одной недоступной возможности.
4. Никаких подмен за спиной человека: задача `bulk` не переезжает молча на провайдера, который потратит на неё вдесятеро больше, — только по решению лида и с записью.

## Авторизация протухла на ходу

Обнаружить посреди прогона, что сессия истекла, — нормально. Крутиться на этом — нет.

- **Один перевод** к другому провайдеру, который готов и имеет нужную возможность.
- **Запись факта** — кто протух, кто подхватил — в файл задачи и в `RUNS.md`.
- **Второго перевода в том же прогоне не бывает**, как и повторов в цикле к тому же провайдеру. Готовых не осталось — задача блокируется с командой входа, волна идёт дальше.
- Работа, уже сделанная в рабочей копии, в ней и остаётся и указывается в отчёте по `workspace-protocol`. Смена провайдера — не повод её выбросить.

## Что докладывает лид

По одной строке на каждую недостающую возможность, с командой для починки. Сами решения маршрутизатора не докладываются — они живут в `RUNS.md`.
