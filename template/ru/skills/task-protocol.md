# Работа с задачами

Три уровня: эпик `E-xx` → фича `F-xxx` → задача `T-xxxx`. Всё файлами в git: доска в чужом SaaS не переживает потерю контекста и недоступна агенту.

## Файл задачи

```markdown
---
id: T-0042
title: Короткое название
feature: F-003
epic: E-01
status: todo          # todo | blocked | in_progress | review | done
owner: backend-dev
reviewer: critic
estimate: 4h
blocked_by: null
touches: [путь/один, путь/два]
risk: high            # high — обязателен человек в ревью
---

## Зачем
Какую боль закрывает. Ссылка на источник требования.

## Приёмочные критерии
- [ ] Проверяемое утверждение, а не пожелание

## Как проверить
Команда или шаги.

## Ход работы
Дневник исполнителя.

## Вопросы
@роль: … — вопросы другим агентам и человеку

## Отчёт
По навыку `handoff-protocol`.
```

## Правила

1. **Статус меняет владелец**, кроме `critic` — он может вернуть из `review`.
2. **`in_progress` дольше суток = брошена.** Вернуть в `todo`, причину в журнал.
3. **Критерии не редактирует исполнитель.** Оказались неверными — вопрос к `planner`, а не правка под то, что получилось.
4. **Задача больше 6 часов — разбить.** Обнаружил в процессе — останови работу.
5. **`done` только после `definition-of-done`.**
6. **Задача без ссылки на фичу не берётся** — это признак, что делают не то.

## Критерии: плохо и хорошо

| Плохо | Хорошо |
|---|---|
| Интерфейс удобный | Действие выполняется за ≤5 шагов без прокрутки |
| Работает офлайн | При выключенной сети операция сохраняется локально и уходит при связи; повтор не создаёт дубль |
| Быстро | p95 < 1 с при 200 одновременных пользователях |
| Правильно считается | Результат совпадает с 12 эталонными примерами заказчика |
