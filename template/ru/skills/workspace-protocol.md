# Рабочие копии: где на самом деле выполняется задача

**Рабочая копия** (box) — это место выполнения задачи: каталог, в котором агент читает и пишет, плюс ветка, в которую он коммитит, если она есть.

Копии живут **вне репозитория**: `~/.agentkit/boxes/<репозиторий>/<номер-задачи>`. Рабочая копия внутри репозитория попадёт в коммит, в индексацию и в линтер того самого прогона, от которого её отделяли.

## Четыре режима

| Режим | Когда | Кому |
|---|---|---|
| `readonly` | в продуктовое дерево никто писать не будет | `critic`, `security-auditor`, `architect`, `domain-analyst`, `planner` — они читают код, а пишут только внутрь `.agentkit/`: задачи, ADR, память |
| `shared` | пишущий по этому репозиторию сейчас ровно один | режим по умолчанию. Самый дешёвый: сам репозиторий, без ветки и без копирования |
| `worktree` | двое и больше пишущих одновременно, либо `risk: high`, либо миграция или массовая переделка | отдельный git worktree на ветке `ak/<номер-задачи>` |
| `sandbox` | операция разрушительная, либо изоляция нужна, а git нет | копия рабочего дерева; без человека ничего не попадает в проект |

Разрешение противоречий, по порядку: роль не трогает продуктовое дерево → `readonly`. Есть хоть одно условие строки `worktree` → `worktree`, а без git это становится `sandbox`. Иначе `shared`.

**Без git одиночный писатель всё равно работает в `shared`** — копия под каждую рядовую задачу сделала бы инструмент неприменимым, — но запуск говорит об этом прямо, потому что отката нет. Лечится `git init`, а не более громким предупреждением.

`shared` — не способ дёшево запустить двух пишущих. Двое пишущих — это `worktree`, даже если их `touches` не пересекаются, см. `parallel-work`.

## Копия принадлежит задаче, а не агенту

Одна задача — одна копия, кто бы в ней ни работал. Следствия:

- `qa-engineer` и `critic` смотрят **ту же** копию, в которой работал исполнитель, а не свежий клон. Ревью другого дерева — это ревью ничего.
- Подкоманда **наследует копию родительской задачи**. Свою не заводит.
- Подкоманда, которой действительно нужна отдельная копия, — это уже не подкоманда: родитель заводит **подзадачу**, и копию получает она.
- **Глубина вложенности — не больше 2.** Дальше никто не скажет, в каком дереве лежит изменение, и лид теряет способность ответить на вопрос «где сейчас находится этот код».

## Порядок слияния

`реализация` → `qa-engineer` → `critic` → `интеграция` → `done`.

**Слияние — отдельная задача, а не побочный эффект `done`.** До прохождения критика не вливается ничего. Вливает `integrator` — он же единственный, кому разрешено разрешать конфликт между работой двух агентов. Слияния с `risk: high` уходят человеку.

## Что писать в отчёте

Каждый агент, работавший в копии, указывает в отчёте по `handoff-protocol`:

- **режим** — `readonly` / `shared` / `worktree` / `sandbox`;
- **ветка** — `ak/<номер-задачи>` либо «нет» для `shared` и `readonly`;
- **незакоммиченное** — осталось ли что-то незакоммиченным и что именно. «Ничего» — это ответ, молчание — нет.

Копия с незакоммиченными изменениями не закрывается, не переиспользуется и не удаляется сборщиком. Именно так неупомянутая работа и пропадает.

## Закрытие копии

1. Проверки зелёные в самой копии.
2. Всё закоммичено либо явно перечислено как оставленное, с причиной.
3. `critic` пропустил → задача интеграции вливает `ak/<номер-задачи>` в базовую ветку.
4. Ветка удаляется, только когда влита полностью. Ветка с невлитыми коммитами остаётся, и копия вместе с ней.
5. Влито и пусто → копия уходит сборщику мусора, см. `resource-limits`.

## Если в проекте нет git

Деградируем по правилам, а не на ходу:

- задачи, которым нужна изоляция, идут в режиме `sandbox`, на копии рабочего дерева;
- **пишущий одновременно только один** — без веток конфликтующую работу некуда сливать;
- интеграция превращается в патч, который применяет **человек** после просмотра;
- лид сообщает об этом в отчёте по прогону: команда стала последовательной, и план обязан это отражать.

Завести систему контроля версий — задача человеку, а не то, что агент делает мимоходом.
