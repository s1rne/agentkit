# Состав команды: наряд и штат

- **Наряд** — сколько экземпляров какой роли запущено сейчас. Считается под каждый набор задач, живёт в `RUNS.md`.
- **Штат** — какие роли вообще есть. Меняется редко, живёт в `.agentkit/state/TEAM.md`.

Оба решает лид. Человеку сообщается, а не согласовывается.

## Часть 1. Расчёт наряда

Алгоритм по шагам, не на глаз.

**1. Взять пул.** Задачи `todo`, не `blocked`, с заполненными критериями.

**2. Вынуть последовательные.** Идут по одной: `risk: high`; любые миграции схемы; первая задача нового модуля — сначала эталон, потом по нему копируют.

**3. Сгруппировать остаток по `owner`.**

**4. Внутри роли разбить на непересекающиеся группы по `touches`.** Две задачи с общим файлом — одна группа.

**5. Экземпляров роли = число групп**, но не больше потолка из `TEAM.md`.

**6. Общий потолок — 5.** Превышает — резать по приоритету фичи.

**7. Проверить обеспечение.** У каждой запущенной задачи должен быть свободный `critic` на выходе. Не хватает — уменьшить наряд, а не пропускать ревью.

### Пример

Пул 7 задач. Одна `risk: high` и одна миграция изымаются. Остаток: 3 задачи `backend-dev` (две трогают общий модуль, третья другой), 2 задачи `reports-dev` без пересечений.

Наряд: **2 × `backend-dev`** + **2 × `reports-dev`** = 4. Затем критики, потом последовательно изъятые.

## Часть 2. Изменение штата

### Когда нанимать

Признак **один**: одна и та же специфическая работа встречается в **3+ задачах** и не ложится ни на одну существующую роль без искажения.

Признаком **не является**: задача сложная (это декомпозиция), задача непривычная (разово делает ближайшая роль), хочется красивой структуры (штат не украшение — каждая роль стоит контекста и внимания лида).

Отдельный источник найма — условия человека из `HOUSE-RULES.md`, навык `house-rules`.

### Как нанимать

1. Написать `.agentkit/roles/<роль>.md` по образцу: что делает, **чего не делает**, жёсткие правила, общий блок.
2. Строка в `TEAM.md`: статус, ответственность, потолок, ревьюер, навыки.
3. Нужна новая процедура — завести навык, а не раздувать определение роли.
4. Запись в `JOURNAL.md`.
5. Сообщить человеку одной строкой. Разрешения не спрашивать.
6. `npx agentkit sync`, если проект использует генерацию конфигов.

### Когда выводить

- Роль не вызывалась две волны → `резерв`.
- Роль стабильно дублирует другую → слить, статус `выведена`.
- Отчёты роли бессвязны → она слишком широкая, разделить.

**Определения не удаляются.** Меняется статус, файл остаётся: удалённая роль через полгода будет изобретена заново с теми же ошибками.

### Потолки

Повышать, если роль стабильно узкое место, а её задачи не пересекаются по файлам. Понижать, если параллельные экземпляры конфликтуют или их отчёты невозможно свести.

**Потолок роли, работающей со схемой БД, — всегда 1.** Две параллельные миграции дают конфликт порядка.

## Что лид обязан знать про каждую роль

Прочитав `TEAM.md`, ответить не открывая определений: чем занимается, сколько экземпляров допустимо, кто ревьюит, какие навыки передавать. Не отвечается — `TEAM.md` неполон.
